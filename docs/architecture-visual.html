Workflows that can pause for the real world — and resume exactly.

AgentTS is durable execution for agent workflows, in TypeScript. A workflow is an ordinary function. When it needs a worker, a shell command, a human answer, or a wait, it calls a trap — and suspends into a snapshot on disk. Hours later, or after a crash, that snapshot plus the journal make the run resumable exactly where it left off: a completed, journaled trap is re-answered from its record, never re-executed. (One deliberate exception to automatic recovery: a run caught mid-drive by a VM replacement sits in running until the coordinator re-drives it — see §7.)

Audience: a developer evaluating or operating AgentTS. The teal parts assume no Muse knowledge; the amber parts assume this deployment. Prerequisites: comfort reading TypeScript — no prior knowledge of AgentTS or QuickJS internals is needed.

01 — Why this exists

Agent work doesn't fit in one process lifetime

A useful agent workflow waits: for a subagent to finish research, for a human to approve a gate, for a cron time, for a test suite. If that wait lives only in memory, any crash, deploy, or VM replacement loses the run. AgentTS moves the wait to disk.

❶ The function is the workflow

No DAG file, no state-machine JSON. You write a normal TypeScript function with branches, loops, and try/catch. The types are the contracts — the host extracts JSON Schema from them on first run. There are no schemas in author code.

❷ Every pause is durable

A trap suspends the QuickJS heap into a blob. The host stores the blob (SHA-256 verified, keyframe + delta chain), appends to the run's JSONL journal, and only then dispatches the work. Resume rehydrates real Errors, not strings.

❸ The journal decides races

Cancel vs. complete, crash vs. failure, dispatched vs. never-dispatched — all decided by journal order. After a crash the host checks the journal before re-dispatching, so a completed job is re-answered from its record, never re-executed.

A minimal workflow

This is the actual quickstart shape — workflows/library/hello.ts plus the trap wrappers every workflow uses:

import { sleep, job, gate, decide, all } from "../src/agentts";

export interface ReviewInput { draft: string; rubric: Rubric }
export interface ReviewResult { verdict: string; score: number }

export default function review(input: ReviewInput): ReviewResult {
  // fan out: two judges in parallel — all() forks, each branch gets its own blob + journal
  const [a, b] = all([
    () => job<JudgeIn, JudgeOut>({ spec: "judge", input: { draft: input.draft } }),
    () => job<JudgeIn, JudgeOut>({ spec: "judge", input: { draft: input.draft } }),
  ]);
  const d = decide<Decision>({ question: "mean score vs threshold…" });
  if (d.choice === "needs-human") gate({ question: "Approve this draft?" }); // ← can hold for days
  sleep({ ms: 100 });
  return { verdict: d.choice, score: (a.value.score + b.value.score) / 2 };
}

Rules that make this work: everything crossing a trap must be clean JSON (checked by toJsonValue() — Date crosses as its ISO string, functions / Maps / cycles throw synchronously at the call site and never dispatch). The entry must be a plain sync function called from global code — module frames cannot suspend, so the host bundles driver + workflow into one global script and refuses any bundle that still contains import/export.

02 — Architecture

Three layers. Nothing skips a layer.

The dependency rule is enforced, not conventional: agentts check --layering runs in the first-run gate and in run.sh on every full run. Layer 1 never talks to Layer 3. Layer 3 never reaches into Layer 1. The swap test proves it — the same workflows run byte-identically under the reference, mock, and real hosts.

DurableTS — C, on patched QuickJS (dquickts) · packages/durablets/

Snapshot-based durable execution and nothing else. It routes traps by type string and waits for an answer. It does not know what a job, gate, judge, or workflow is.

03 — Execution

How and where a run executes

There is exactly one way to start a run — there is no in-process drive mode. run --wait is not a second path; it is submit → queue run → result. Tap each stage.

Where it runs — physically

Everything is on one VM today. The host is a Bun process spawned per CLI invocation. The C host is spawned once per run-slice (spawnSync, blob + JSON over stdio) — there is no long-lived daemon. Pool jobs run either as Bun worker processes on the same VM or as Muse subagent sessions. State lives under a state dir: production is ~/workspace/agentts-state/, tests always use scratch dirs. That single-VM shape is a Muse-harness choice, not a core requirement — the blob protocol doesn't care where the next slice runs, as long as it runs an engine with the same snapshot format identity (BRA-132 — a logic-only engine change resumes).

Sub-workflows: run()

A workflow can call another workflow with run<In, Out>({ workflow, input }) (BRA-105). The parent suspends on the run trap; the child gets its own runId (<trapId>/child), its own journal, frozen closure, and checkpoint chain — pinned inside the parent's frozen copy at parent submit, so editing the child afterwards changes nothing. A child failure throws at the parent's call site with the child's error name and message preserved; a child held at a gate holds the parent too.

04 — Component view

One trap, end to end

The trap-dispatch split (BRA-75) is the detail that makes crash recovery exact: the host journals intent before dispatch and the answer after, so a re-drive can tell “dispatched” from “never dispatched.”

Fig. 2 — A single trap's round trip. sleep / cron skip the adapter entirely: the host answers them itself and journals a clock-advance (virtual clock in tests — a 2-hour sleep costs ~0 ms of wall time; real wall clock in production). A gate answered HOLD suspends the run until deliver-gate arrives — minutes or days later, in a different host process.

* decide is narrow by design: the local model parses machine-readable signals out of the question (mean score vs. threshold, misses, keyword scoring) and falls back to the first option at confidence 0.5. It is not a general reasoner. Anything needing real judgment is a job.

Combinators fork for real

all / any / race fork the snapshot: each branch gets a copy of the blob and its own journal. The parent snapshot is untouched (SHA-256 checked before fork vs. before join); a branch's write to fork-time shared state is discarded. race losers are cancelled; cancellation propagates deepest-first and is sticky.

Traps can't hide in callbacks — yet

A trap inside 15 probed native-builtin callbacks (e.g. inside Array.map) is refused at first run, naming the callback and the fix — use a plain for loop (BRA-129, option b). The snapshot format has no representation for C builtin loop state, so supporting it would be an engine redesign, not a patch.

Call sites travel with the trap

Wrappers attach {file, line, column} (bundle coordinates) under a reserved key. The host strips it before dispatch — no adapter ever sees it — and journals it as the trap's site, so the profiler can map every trap back to workflow source via the pinned bundle + source map.

05 — The Muse environment

The worker pool, the tick agent, and three roles

This section is the Muse harness. None of it is in the core or the host's contract — it's what the muse adapter plugs into Layer 3. Another harness would build a different version of this whole section.

Fig. 3 — The Muse deployment. One protocol file (worker-protocol.ts) is shared by server, adapter, worker loop, and CLI, so the wire shape cannot drift. Enqueue dedupes on trapId — exactly one job per trap, even after a crash.

Leases keep dead workers honest

A running job holds a lease — by default the cost model's p90 for that spec × 2, clamped to [60 s, 30 min] — max 3 attempts. Heartbeats extend it; at half-lease with no completion the server nudges once (post a status note, keep working). Silence → lease expires → job re-queues. A late completion from a worker that lost its lease is a 409: stop, don't retry.

Affinity is a cache, not an address

The scheduler prefers the worker that most recently completed a spec — its live session context is the cache. A job waits for its warm worker at most ~2 s before falling back to the oldest waiting job, and affinity goes cold after 30 min. workerId is a self-asserted handle for lease ownership, affinity, and debugging only: there is no registry, no enrolment, no way to address a job to a worker. The model is pull — workers ask, the scheduler picks the best queued job for that worker.

Memory lives with the spec

What survives a worker is not the worker's memory. Workers post durable learnings per spec (POST /note → notes/<spec>.md); the next worker on that spec — possibly a cold one after a context reset — reads them. Jobspecs themselves are prose files, hash-cached: a worker re-reads a spec only when its SHA-256 changed. File effects return as full contents (1 MB cap) and are never auto-applied — the coordinator reviews them.

The tick agent's one job: keep the machine churning

It long-polls GET /tick (60 s, max 120 s; at most one pending — a second is a 409). On run-submitted it drives the queue; on workflow-completed/failed it records a delivery in the outbox (a failed delivery carries needsAttention: true — that is the escalation); on gate-held it escalates and waits. It heartbeats via /tick-beat before and after long actions. On restart it does a catch-up sweep first — queued runs get driven, undelivered terminals get delivered, held runs get escalated, running runs get escalated as stuck. It never flips a running entry back to queued and never uses queue repair --force: re-driving could double-execute a side effect that happened but wasn't journaled yet, so that call belongs to the coordinator, who can confirm the holder is actually dead.

06 — Scheduling

Two layers, because the backlog is not the queue

Both schedulers are pure logic — no I/O, decisions returned as data so the caller can journal them. That purity is what makes them testable and portable.

Layer 1 — Admittance · agentts admit

Which backlog tasks become runs?

  • Priority order (Linear 1 urgent → 4 low; absent = medium) under a WIP limit, default 3.
  • Each task maps to a library workflow via --map, --workflow, or a workflow:<name> label. No mapping → skipped as needs-workflow, never admitted to nothing.
  • Waiting ages priority one step per 7 days, capped at two steps.
  • In-flight tasks are never re-admitted; a terminal link frees the slot. admit never executes a run itself.
  • Task↔run links are comments ([agentts] on Linear) or rows in task-runs.json — v0 never changes issue state. Closing issues is the coordinator's job.

Layer 2 — Dispatch · pool server, at dequeue time

Which queued job does this asking worker get?

  • Effective priority first — base priority improved one step per 5 min waited, capped at two steps (the starvation guard).
  • Then affinity, inside the tier only — a warm job never promotes out of its tier.
  • Then estimated cost — shortest first; unknown costs sort as the tier average, never as zero.
  • Quotas (pool size, CPU slots, decision rate, tokens/hour) are enforced by the server around selection: a blocked pick is excluded, selection re-runs, and the exclusion is journaled (quota-blocked). One blocked job never starves the queue behind it.
  • The cost model behind the estimates is real actuals per call site (cost-actuals.jsonl: mean / variance / p90 / n), not guesses.

The host's run queue itself also drives in priority order, FIFO inside a tier — same discipline, one level up. The Muse-specific part here is only the backlog source (Linear, via the coordinator). The two-layer split and the ordering rules would work unchanged over GitHub Issues, a local file, or a database table.

07 — Durability

Everything that matters is a file

No database, no in-memory-only state that matters. One state dir holds the whole system — which is why a VM replacement is survivable: the new VM mounts the same workspace and the journals, blobs, and queue are simply there.

journals/<run>.journal

JSONL, append-only, one appendFileSync per event. The source of truth. Format v2: every event carries wallTs; trap results carry adapter, worker, wallMs. Branch runs get their own journals.

blobs/ + keyframes/

Latest keyframe copy + latest delta per run, plus a content-addressed keyframe store (BRA-90) and a checkpoint manifest — written last, so it is the commit point. Blobs are SHA-256 verified on store and on restore.

frozen/<hash>/

Frozen workflow closures: entry + transitive imports + the agentts module, content-addressed. Built in a temp dir and renamed into place — a crash mid-freeze never leaves a partial copy. A missing frozen copy on resume is a loud refusal, never a fallback to the live file.

queue.json (+ .bak)

The run queue. Written atomically (tmp + rename); a corrupt file is recovered from the backup and journaled as queue-recovered — never silently treated as empty.

runs/ · slices/ · cache/

Persisted registry entries, the generated driver + pinned bundle and source map per run, transient slice files (.snap/.out/.log), delivered gate answers, and the extraction cache keyed by content hash.

worker-jobs/ · deliveries/ · tick/

Pool store (+ backup, jobs.log, scheduler.log), the delivery outbox, tick-agent liveness (tick/state.json), the driver lock, and corruption.log — quarantined bad lines, kept for forensics, deduped, append-only.

Crash recovery, in order

  • C-host crash mid-slice (exit 1, no lifecycle event) ≠ workflow failure (lifecycle failed in the journal). The former resumes from the last intact blob (host-crash → host-crash-resumed); the latter is never retried.
  • Crash on the first slice retries from scratch, bounded at 3 — no trap was dispatched, so it's idempotent.
  • Sleep deadlines are durable (G11): recorded at dispatch; a host killed mid-sleep waits only the remainder on resume.
  • Format-identity mismatch refuses loudly (BRA-132): a resume under a different snapshot format identity — blob-header signature + dquickts pin + host native names — marks the run failed but leaves the blob, so restoring the matching engine and re-queueing can still resume it. A release that changed only durablets.c logic leaves the identity unchanged, so parked runs resume.

Drive integrity

  • Driver lock: one driver per state dir (holder.json + 10 s heartbeat). A second driver refuses. Only a human who confirmed the holder PID is dead may break it with --force.
  • Queue repair runs before every drive: journal says completed → mark done; intact blob after a crash → re-queue to resume; trap activity but no registry entry → leave for a human (re-driving would restart and could double-execute).
  • The test suite proves the chunking: 72 sections in the inventory (37 in tier 1), slowest tier-1 section 125 s in the latest run, none over five minutes; run.sh resumes per section from markers, and the tier-2 kill test (SIGTERM mid-run → resume → full pass) is a standing test, not a hope.
  • Known gap: workflow auto-resume after a driver death is detected (watchdog, ~30 min) but not automatic — a running entry waits for the coordinator by design. See §9.
08 — The important distinction

What's Muse, what's the harness, what's universal

AgentTS was built inside Muse, so the Muse shape is the one that's proven. But the architecture was designed so the Muse parts are exactly the replaceable parts. Here's the honest split.

How it works here, concretely

  • Coordinator = Meroki, a named Muse agent in the main session. It admits Linear tasks, writes workflows, spawns the tick agent and workers as subagents, reads the delivery outbox, answers gates, and closes issues.
  • Workers = Muse subagents running the get-job loop by hand (get-job.ts / complete-job.ts per WORKER.md), each with a stable workerId and its own workspace directory on this VM. A Bun script worker runs the identical loop as the proof leg.
  • Tick agent = a persistent Muse session driven by TICK-AGENT.md, restarted by a cron watchdog when it goes silent with work pending.
  • Jobspecs = prose files a subagent reads and interprets — the “worker” is a full LLM session with tools, not a function call.
  • Everything shares one VM and one filesystem — state dir, frozen copies, per-worker workspaces, and the pool server on loopback.

What Muse gives this design

  • Subagents that can be spawned on demand and keep a warm session context — which is precisely what affinity exploits.
  • A coordinator with judgment in the loop for the decisions the system deliberately refuses to automate: admitting work, breaking locks, answering gates, closing issues.
  • Long-lived sessions (tick agent, workers) that can block on a 60-second long-poll and act when it returns.
  • Tool access inside jobs: a “judge” job isn't a model call, it's an agent that can read the repo, run tests, and post notes.

None of those four are in the core's or host's contract. They're properties of this deployment.

What you keep, untouched

  • Layer 1, verbatim. The C core, blob protocol, combinators, cancellation, JSON boundary. It has never heard of Muse.
  • The agentts module and every workflow. Workflows import traps, not environments — the swap test is the proof this holds.
  • The journal format, frozen copies, state layout. A run frozen under Muse can in principle resume under another host build with the same snapshot format identity.
  • The scheduling rules and cost model. Pure logic; only the backlog source changes.

What you rebuild, in your harness's idiom

  • A new Layer 3 adapter — the only code you must write. It implements the same 4-trap answer() seam.
  • Workers: in Claude Code they'd be CLI sessions or API-driven loops; on a server, container jobs or a job queue (BullMQ, Temporal activities, K8s Jobs); for pure model work, direct API calls with no agent session at all.
  • Tick agent: becomes a cron job, a systemd service, or a small daemon doing the same sweep → drive → deliver → escalate loop. It never needed to be an LLM — it needs judgment only at escalation, which is the coordinator's job anyway.
  • Coordinator: a human operator, a different orchestrating agent, or a thin control plane. The role (admit, gate-answer, lock-break, close) is the contract; Meroki is one occupant.
  • Pool transport: loopback HTTP is a single-VM convenience. Multi-machine means the same protocol over real HTTP with auth — workerId would stop being self-asserted, which is the first thing to harden.

The test for “is this portable?”

Ask: does it appear in a workflow file, the journal format, or the trap/blob protocol? If yes, it's portable — changing it would break existing runs. If it lives in plugins/muse/, a standing-instructions file (WORKER.md, TICK-AGENT.md), or the coordinator's habits, it's harness. The layering lint draws exactly this line in code: core + host may not import anything Muse-specific, and workflows may not import anything under plugins/ at all.

Profiler: the journal, rendered

agentts profile <runId> is read-only — it never constructs a Host and never dispatches. It folds each run's journal (+ branch journals) into a timeline: per-trap-type counts, fork/join counts, gate holds, clock advances, and per-trap wall times (wallMs, or the dispatch/result split the BRA-75 journal makes possible: queue-wait vs. execution). The axis is event order, not time; v1 journals report wall durations as unknown, never invented. --format html emits a single self-contained page.

The CLI is the API

There is no installed binary and no server API for runs: agentts is bun src/cli.ts. run / result / status / check / deliver-gate / queue list|run|repair / admit / sync-task / cost-model / profile / worker serve|status|cancel / deliver-result / deliveries / escalate / watchdog / version. Exit codes: 0 done, 2 held at a gate, 1 error/refusal. The tick agent's hot path moved to HTTP driver endpoints (BRA-116) because each CLI spawn cost ~400 ms of module loading — submit deliberately stayed CLI.

Inline workflows

agentts run - … reads workflow source from stdin and materialises it, content-addressed, under .agentts-scratch/inline/<hash>.ts — the frozen copy is the durable record, nothing is deleted, and relative imports resolve against that directory. Useful for one-off runs without writing a file into the library.

09 — Honest limits

What is not built

From docs/ARCHITECTURE.md §12 (the auto-resume rule is §5.3), kept current with the code. A living document earns trust by keeping this section accurate.

  • No named workers, no routing to a specific worker, no per-worker memory — undecided (BRA-50), deliberately. Affinity + per-spec notes are the whole identity story until Brandon decides otherwise.
  • No C-host daemon — one process spawn per slice. IPC is a later optimisation.
  • No async adapters in v0 — answer() is synchronous; pool adapters block inside it.
  • No general reasoner in decide — by design; judgment is a job.
  • No versioned release or hosted service — public MVP, host v0.
  • Crash during an exec dispatch re-runs the command — visible in the journal as a second trap-dispatch marked redispatched: true, not silent, but a duplicate execution.
  • A gate answer can be lost in the sub-millisecond window between consumption and the trap-dispatched write; recovery is human re-delivery. Unexercised by tests.
  • Workflow runs don't auto-resume after driver death — state survives and detection is automatic, but a running entry waits for the coordinator (safety rule, §5). The suite, by contrast, resumes automatically per section.
  • Pre-BRA-71 runs carry no frozen copy or engine version and resume from the live file, unchecked.
  • The bench gate is flaky (BRA-107) — a green gate is not yet stable evidence; a red one is not yet evidence of a regression.
